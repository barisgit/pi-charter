pi-charter doctrine proposal

Dumb-smart charters: a thin loop around strong Markdown doctrine

The architecture should stay simple: the runtime keeps the charter alive, shows the next legal move, and blocks bad exits. The intelligence lives in Markdown prompts, skills, and persona files so better future models get better at the workflow instead of fighting a brittle orchestrator.

Design thesis: copy Codex and Claude's best idea, not their exact product. A goal loop can be dumb and still powerful: durable objective, explicit stopping condition, continuation pressure, fresh status, and a few hard gates where agents usually cheat.

01 · The loop

PLAN does not ask. If it lacks authority, it may route to CLARIFY when allowed.

CLARIFY may ask, but only in non-autonomous runs.
CLARIFY does not trigger idle reprompts.
CLARIFY returns to PLAN with answers/context.

LOCK PLAN is reached from PLAN only after objective, stopping condition, and initial map are adequate.
PLAN and every later non-terminal stage get idle reprompts when the agent and subagents go idle.
LOCK PLAN authorizes execution until completion, replan, or true give-up.

ORIENT -> SET CHECKPOINT -> EXECUTE -> INSPECT

INSPECT fails:
  record findings -> EXECUTE fixes the same checkpoint

INSPECT passes:
  DECIDE

DECIDE:
  complete if stopping condition + VAL evidence pass
  continue directly to next checkpoint if work remains and the map still fits
  replan only if the map is stale, then go to next checkpoint
  give up only if impossible, blocked, or budget exhausted

02 · The split: Markdown intelligence, tiny runtime

Markdown

Doctrine and judgment

Prompt files explain how to behave: what “set checkpoint” means, how QA should inspect, how to replan, when to give up, and how to avoid V0 exits.

  • stage instructions
  • persona prompts
  • gate doctrine
  • templates and examples
Runtime

State and legal moves

Code owns charter state, legal next actions, reminders, Ralph reprompts, and gates. It may attach Markdown doctrine snippets, but Markdown never decides what is legal.

  • current stage/checkpoint
  • legal nextActions
  • missing evidence
  • completion blockers
Agent

Actual work

The root agent remains the loop driver. It reads the rendered status packet, uses doctrine snippets as coaching, delegates when useful, implements/researches, and records evidence.

  • implementation strategy
  • research synthesis
  • delegation
  • replanning judgment

Pure guidance, no legal moves

Stage Markdown is not config. It contains durable advice the status renderer can quote beside code-defined rules.

# Inspect

Inspect like an outside verifier, not like the implementer.

Good inspection answers:
- what was reviewed or tested
- what evidence/artifacts were produced
- what risks remain
- whether the checkpoint is credible from a user/runtime perspective

Avoid:
- rubber-stamping because tests passed once
- relying only on the implementer's claim
- skipping real QA for user-facing behavior

04 · What is state-machine driven?

Runtime concernReasonShould stay dumb
Stage Know whether the agent is planning, executing, inspecting, deciding, or complete. Do not infer implementation quality from code. Just track loop position.
Checkpoint Bind the current slice to an evidence target so the agent cannot drift into easy unrelated work. Do not over-model milestones. A checkpoint can be a short Markdown statement plus linked VALs.
Evidence gates Agents self-deceive at completion time. Code should refuse completion without passing VAL evidence. Do not judge aesthetics or architecture in code. Require typed review/QA/readiness evidence instead.
Transitions Prevent bad exits: failed inspect must return to execute; active charters must not silently stop. Do not schedule workers. Return legal next actions and let the root agent drive.
Reminders Inject current state and doctrine snippets into context/status surfaces. Reminders are not turns. They can appear anytime and should stay status-shaped, not static nags.
Ralph / idle reprompt When the agent and subagents go idle, start a new turn for any non-terminal stage except Clarify. This is not a reminder. It is a reprompt delivery mechanism, guarded by no-tool suppression.

05 · What is Markdown-driven?

Stage coaching

What good planning, execution, inspection, and replanning look like. These files do not name legal transitions; they make the current step less sloppy.

Profile behavior

discovery-first starts with inventory/research/spikes. spec-ready starts with coverage extraction. Same loop, different prompts.

Persona behavior

Reviewer, QA, readiness, and planner-critic should be mostly prompt contracts. Runtime only needs their expected evidence shapes.

Gate doctrine

What counts as sloppy V0, what milestone QA means, how stale evidence should be treated, and what makes completion or give-up claims credible.

06 · How agents learn what is next

Return a deterministic next-action packet

charter_status should not just say “active”. It should explain the loop position and the next legal moves in a compact status block.

stage: inspect
checkpoint: M2 CLI surface
objective: Make pi-charter milestone-driven
stoppingCondition: VALs pass + readiness evidence

reminderMode: inject status/doctrine without starting a turn
autoLoop: reprompt on idle unless stage is clarify or terminal

codeDefinedRules:
  legalNext:
    - run checkpoint QA/review
    - record typed evidence or findings
  blockedForComplete:
    - VAL-READINESS has no readiness evidence

doctrineSnippets:
  - path: doctrine/.../stages/inspect.md
    excerpt: "Inspect like an outside verifier, not like the implementer."

Inject a stage-specific reminder

The reminder should be a steer, not a nag. It is rendered by code from current state, code-defined next actions, and short doctrine excerpts. Ralph may reuse this content, but only Ralph starts a new turn.

07 · Reminders vs Ralph loop

Reminder

Context injection, not a turn

A reminder is status/doctrine text the runtime can inject into context, widgets, or tool responses anytime. It helps the current turn stay aligned, but it does not wake the agent or create work by itself.

Ralph / idle reprompt

Starts the agent again

If the root agent and async subagents are idle while the charter is in any non-terminal stage except CLARIFY, Ralph sends a fresh reprompt so the agent continues.

No-tool suppression

Prevent spin

If a continuation turn produced no useful action, suppress blind repeat. The next reprompt should present fresh code-defined next actions and blockers instead of replaying stale prose.

Fresh status

No stale loop prompts

Both reminders and Ralph reprompts render from current charter_status: stage, checkpoint, drift, missing evidence, legal next actions, and blockers.

08 · Minimal hard gates

Only hard-code what agents reliably cheat on. Everything else stays in Markdown doctrine and subagent prompts.
  • Clarify is the only ask-capable phase, and only in non-autonomous runs.
  • No Ralph idle reprompt while in Clarify.
  • No lock without objective and stopping condition.
  • No post-clarify “should I continue?” asks.
  • No completion without passing VAL evidence.
  • Failed inspect routes back to execute.
  • User-facing checkpoint needs QA/readiness evidence.
  • Changed plan/criteria makes stale evidence visible.
  • Budget exhaustion routes to give-up, not fake success.
  • Every other non-terminal stage gets a Ralph reprompt when idle and no subagents are running.

09 · Why this survives model improvements

Too-smart systems become obsolete when models improve. They encode yesterday's agent limitations into code. This design keeps the runtime as a small status renderer and gatekeeper. Better models read the same Markdown coaching more intelligently, produce better checkpoints, write better QA briefs, and replan better without requiring a new scheduler.

The runtime should be boring: doctrine loading, excerpt selection, nextActions, evidence gates, reminder injection, Ralph idle-reprompt delivery, and continuation suppression. The prompts should be excellent.
