Research Brief · 2026-05-14

How four coding agents track goals, plans, and missions

pi-goals today is one durable text reminder. Codex, Claude Code, and Factory Droid have all moved past that shape — toward typed step DAGs, post-turn evaluators, validation contracts, and orchestrated missions. This report compares them, scores them, and lands the successor concept: pi-charter. It is not just pi-goals renamed; it is a binding charter.md (Objective / Criteria / Scope) connected to a macro DAG, evidence, verifier personas, and a smart-Ralph loop.

The verdict

pi-goals is structurally the weakest of the four. It persists state to disk (good), but the rest of the goal kernel — adaptive reminders, decomposition, verification gates, autonomy coupling, sub-agent handoff — is either missing or static text.

Highest-leverage direction: replace v1 goals with pi-charter — a charter-scoped post-turn evaluator plus a criteria-backed completion gate and macro DAG. The evaluator is the first slice; the charter is the durable concept.

Capability ranking: Factory Droid ≥ Claude Code ≳ Codex ≫ pi-goals

03Codex — /goal (SQLite + budget loop) and update_plan

04Claude Code — /goal, Plan mode, Task DAG, Hooks

The most complete single-session goal stack: durable conditions, separate-model evaluator, gateable hooks, DAG-shaped tasks, plan-mode permission, all composable.

/goal

Durable condition + evaluator

  • 4 KB condition; auto-starts next turn until satisfied
  • Separate small model (Haiku) reads condition + transcript after every turn → yes/no + reason
  • "No" reasons injected as fresh next-turn guidance (adaptive reminder)
  • Restored on --resume (counters reset)
  • Built on a prompt-based Stop hook — replicable by users

  • TaskCreate / TaskGet / TaskList / TaskUpdate / TaskStop
  • Dependencies in TaskUpdate → blocked vs ready computed
  • Hook events fire on TaskCreated, TaskCompleted
  • Both events have decision-control → a hook can refuse completion

05Factory Droid Missions — multi-session orchestrated workflows

Missions externalize state to git + shared files, run TDD per feature, validate per milestone with scrutiny + black-box agents, and loop fix-features until validation contract is green. Median 2 h, tail to 16 days. Requires High autonomy.

08pi-goals gap ladder

Three tiers by leverage. Tier S = biggest single-shot wins; Tier A = high leverage, moderate complexity; Tier B = useful, lower urgency.

Tier S biggest wins

  • S1 · Post-turn evaluator A cheap model judges are we done? what's next? after every assistant turn; result is the next-turn reminder. Solves static-text drift, no completion gate, no auto-continue, all at once. model: Claude Code /goal
  • S2 · Verification gates with evidence binding Add verifyCommand? / verifyPrompt? per criterion. Block charter_manage({action: 'complete'}) unless each criterion has a recorded pass. Land results in the existing evidence[]. model: Factory validation-contract.md + Claude TaskCompleted

Tier A high leverage

  • A1 · Sub-task DAG Optional tasks[] with id/title/status/dependsOn[]/verifyCommand?. Unlocks dependency-aware "what next" for S1. model: Claude TaskCreate / TaskUpdate
  • A2 · Gateable goal events Emit pi-goal:before-complete and pi-goal:criterion-ready with decision control; let other extensions veto completion. model: Claude hooks
  • A3 · Compaction-aware reinjection On PreCompact/PostCompact, write a condensed goal block back into context so criteria survive summarization. model: Claude PreCompact / PostCompact

Tier B nice to have

  • B1 · Plan-mode coupling Refuse completion in read-only host modes; permit criterion proposals only.
  • B2 · Sub-agent handoff envelope When a subagent spawns, auto-include objective + relevant criteria + nextAction in its prompt.
  • B3 · charter.md / AGENTS.md hierarchy Mirror Codex's load order for project instructions; per-charter "done when" lives in charter.md §Criteria. model: Codex AGENTS.md
  • B4 · Resume reset semantics Like Claude /goal: keep condition; reset turn / time / token counters. model: Claude /goal

09Proposed pi-charter v2 — three-tier architecture

Most-powerful v2, not minimal. Renamed pi-goals → pi-charter; kernel object is Mission; tools are mission_*; slash command is /charter. Three durable primitives in pi-charter (Mission, Contract, Macro DAG) plus one ephemeral primitive in pi-dag-tasks (Tactical tasks). Bridges go one direction only. Full design in v2-brainstorm.md + orchestration-layering.md.

Disambiguation rule: mission = why + done; contract = done means what; feature = durable work unit that produces evidence; tactical task = next step (turn-to-turn). v2 strengths — what makes it the most-powerful version

1 · Contract layer

Done means what, in writing

  • VAL-* assertions authored before features (Factory)
  • Per-criterion verifier: command · prompt · hook · manual
  • Fresh-evidence invariant: complete blocked until evidence post-dates verifier change
  • Side-car bitmap (state-charterId.json) so contract markdown stays clean
2 · Macro DAG

Durable work-breakdown

  • Features grouped into milestones, survive compression + resume
  • fulfills[] join into contract → coverage computable
  • Three drift views: uncovered · unverified · wasted work
  • Two new drift views: stuck features · milestone debt
3 · Adaptive evaluator (folds intent-sentinel)

Drift signal every turn, two modes

  • Separate cheap model + reasoning effort (Factory split)
  • mission-scoped when active — cites criterionId / featureId or steer is dropped
  • free-form when no mission — verbatim intent-sentinel behavior
  • Returns verdict + reason + proposedNextAction; never gates completion
4 · Asymmetric authority

Safe completion

  • Model can create, propose-complete, record-evidence
  • System reserves pause, resume, budget, force-complete
  • Token + wall-clock + turn budget enforced atomically
  • charterId UUID stale-write protection (Codex pattern verbatim)
5 · Handoff envelope

Subagent results, structured

  • Per-handoff {command, exitCode, observation} triples
  • discoveredIssues with explicit accept / dismiss + justification
  • Subagent inherits active charterId via opaque metadata; emits envelope on return
  • Parent applies envelope: evidence + criterion updates + event log
6 · Gateable hooks

Independent vetoes

  • Mission-level: charter:before_complete · charter:before_amend_contract · charter:before_force_complete
  • Plan-level: feature:before_complete · milestone:before_gate
  • Handlers: shell · HTTP · prompt-based · agent-based
  • review phase + hook = two vetoes before completion
7 · Planning phase

Plan stress-tested before activation

  • Distinct planning status; contract + plan co-authored
  • Adversarial pass: uncovered scope · orphan features · cyclic preconditions
  • User approves → plan_approved event → digests lock
  • amend_contract requires re-verification of affected criteria
8 · Compaction-aware

Survives /compact + --resume

  • All durable state in <project>/.pi/charters/<charterId>/, never transcript-only — per-project, not per-machine
  • PreCompact reinjects current evaluator reason
  • Resume re-runs evaluator before next turn fires
  • Auto-pause on interrupt, auto-resume on session re-entry
9 · Bundled personas + spawn substrate

Contract-aware verifiers ship with the extension

  • pi-charter ships charter-verifier + charter-planner-critic as internal-scope personas in this pre-ADR sketch — invocable only by extension code, never advertised to root LLM
  • Resolver search path: <context-dir>/agents/ → ~/.pi/agent/agents/ → extension-registered. Users override by file-shadowing
  • Bundled persona frontmatter declares its tool allowlist explicitly (incl. charter_record_evidence + charter_handoff_apply)
  • Two pi-subagents TS surfaces: spawn({agent, task}) for named/stable + spawnRaw({systemPrompt, prompt}) for dynamic state (the old separate-model supervisor idea embedded live criteria status + last 3 verdicts)
  • Opaque metadata passthrough on hook events — pi-charter tags spawns with "pi-charter.charterId"; pi-subagents never reads it. No mission vocabulary leaks downstack
  • Substrate payoff: same mechanism works for any future pi-extension (pi-qa, pi-docs, pi-deep-research) — ship bundled personas, use spawnRaw for live prompts, tag with namespaced metadata
10 · Autonomous-first + upstream spec acceptance

Mission is the alignment rail, not the approval gate

  • Upstream orchestrator (Symphony / external planner / direct prompt) drafts the spec; spawned agent calls charter_manage({action: 'create'}) itself and fills in the charter + plan — agent-initiated, no substrate magic
  • charter_manage({action: 'create', objective, budget?, idempotencyKey?}) — three optional fields, minimal surface. Spec handling is plain English in the spawn prompt; the agent reads files with its own tools. Symphony writes <charterDir>/charter.md directly when it has a pre-baked charter; planning notices the file and skips authoring. No contractPath/charterPath, no contractDraft, no planDraft, no autoApprovePlan, no completionMode — do not re-add
  • Three nested grains: Symphony (inter-mission) → pi-charter (intra-spawn) → pi-dag-tasks (per turn). Each layer owns its decomposition
  • Plan approval is headless by default: charter:before_lock_plan hook fires; if no subscriber gates, plan auto-locks. Bundled TUI approver subscribes when on (charter.config.json: tuiApprover: on, default on; PI_CHARTER_TUI=off overrides). CI / agent loops set off and run unattended
  • Evaluator never gates completion — only the verifier + charter:before_complete hooks do (Codex asymmetric-authority pattern). HITL is entirely out of pi-charter scope; lives in subscriber extensions
  • Three first-class entry points, all explicit: charter_manage({action: 'create'}) tool (agent), /charter <objective> or /charter new slash (user), or pi --charter-objective "<text>" / pi --charter-resume <id> CLI flags via pi.registerFlag(). pi-charter never silently wraps a session based on inferred intent
11 · Session ↔ mission binding (filesystem, not transcript)

Multi-mission per project; agent never picks up someone else's mission

  • Per-project scope: <project>/.pi/charters/<charterId>/ (mirrors v1 .pi/goals/). Multiple missions can coexist; index.json registry lists them. Worktrees inherit naturally
  • Two-file binding with no custom transcript message: forward state.json.sessionId on the mission, reverse ~/.pi/agent/sessions/<sid>/charter.json on the session. Compression-safe; forward wins on disagreement
  • Resolution order for any mission_* tool with no charterId arg: explicit arg → reverse session file → error if multiple active (explicit beats clever)
  • Agent surface: charter_manage({action: 'create'}) auto-binds the calling session. No charter_claim tool — agent never adopts a charter it didn't create
  • User surface: /charter resume <id> slash + pi mission resume <id> CLI rebind; /charter clear unbinds. Switching ownership between sessions is human-only
  • /fork gets a new sessionId with empty sessions/<newSid>/; can read but not write mission state until user runs /charter resume. One owner at a time. Subagent children never bind — charterId reaches them via metadata passthrough only
Boundary with pi-dag-tasks: pi-dag-tasks keeps owning the tactical layer (turn-to-turn todos, ready/blocked, persistent widget, reminders) as a fully separate extension. No new fields, no pointer back into missions. Coupling lives entirely on the missions side: pi-charter optionally subscribes to tasks:after_complete hook events for context. Neither extension imports the other; communication is via the hook bus and shared file directories only. The user-visible rule: features are durable work units that produce evidence; tactical tasks are this-hour's todos — useful with or without an active mission.
Boundary with pi-subagents: pi-subagents stays mission-unaware. pi-charter consumes only its public surface — spawn / spawnRaw / registerPersonaDir — and hook events with passthrough metadata. CI grep guard forbids the tokens mission · charterId · criterion · criterionId · feature · goal_ inside pi-subagents source. The substrate stays a universal spawn mechanism for every future pi-extension; coupling lives entirely in the upper layer.
intent-sentinel → folded. ADR 0009 superseded that idea with deterministic Ralph reprompts driven by charter_status. This section is historical only.
